Architecture

Five packages inside a Backstage 1.55 backend and app. A deterministic engine decides; Backstage supplies the sources, the permissions and the agent tool path.

Packages

PackageRole
@contextverity/coreDeterministic, provider-neutral engine: canonicalization, digests, the policy model, the verdict engine, the receipt service and OpenTelemetry API instrumentation.
@contextverity/plugin-contextverity-commonShared types and the contextverity.receipt.read permission.
@contextverity/plugin-contextverity-nodeBackstage Software Catalog source provider and Backstage Permission Framework authorizer.
@contextverity/plugin-contextverity-backendBackstage backend plugin: HTTP API under /api/contextverity/v1, a Knex receipt store on the Backstage database service, a retention task, and the two actions registered in the Actions Registry.
@contextverity/plugin-contextverityBackstage frontend plugin for the new frontend system: receipts list and receipt detail with provenance and drift.

Resolution and verification

Resolve

  1. A caller sends POST /api/contextverity/v1/resolve with a subject, a purpose and categories.
  2. ContextVerity selects the context policy that grants this consumer, purpose and subject (the grant). No matching policy, an ungranted category, a disallowed source kind or a classification above the ceiling refuses the request.
  3. The Permission Framework is asked whether the caller may perform catalog.entity.read on each entity.
  4. The catalog provider fetches normalized records: owner, lifecycle, dependencies, provided APIs, API definition digest, TechDocs reference and classification.
  5. Each record is digested with SHA-256 over canonical JSON (RFC 8785 style). The receipt is stored, immutable and integrity-tagged with HMAC-SHA256, and returned with the context.

Verify

  1. A caller sends POST /api/contextverity/v1/receipts/:id/verify.
  2. Binding: consumer, issuer and integrity of the stored receipt.
  3. Intent: subject, purpose and requested scope against the receipt.
  4. Policy: removed, narrowed or changed since issue.
  5. Time: the receipt's TTL.
  6. Permissions are re-evaluated for the consumer, and sources are re-fetched and compared field by field.
  7. Every difference becomes a typed drift item with an effect. The verdict is the strongest effect.

Verdict semantics

VerdictMeaningWhat the caller should doExamples
VALIDMatched source, permission and policy state at verification time.Act on the recorded context. Verify again before later actions.No change; unrelated entity changed; relation order changed
REFRESHNo longer current, but not prohibited.Re-resolve to get a new receipt before acting.OWNER_CHANGED, API_CHANGED, TTL_EXPIRED, ENTITY_RECREATED
DENYCurrent authorization, classification, policy or binding no longer permits it.Do not use this context.PERMISSION_REVOKED, CLASSIFICATION_RAISED above the ceiling, POLICY_REMOVED, CONSUMER_MISMATCH

No language model is involved in any decision. Effects come from the drift code, the situation and the policy.

The MCP integration boundary

ContextVerity registers two actions in the Backstage Actions Registry: contextverity:resolve-context and contextverity:verify-receipt. The official @backstage/plugin-mcp-actions-backend exposes them as the MCP tools contextverity.resolve-context and contextverity.verify-receipt.

The integration is explicit and advisory. ContextVerity is not an MCP server of its own, not a gateway, and it does not intercept other actions: Backstage provides no supported hook for that. An agent, or the harness around it, calls verify before acting and honours the verdict.

Identity notes

  • Receipts bind to the consumer that resolved them; another consumer presenting the receipt yields CONSUMER_MISMATCH.
  • Through the MCP Actions backend, a static-token agent is forwarded as plugin:mcp-actions. Per-agent identity is preserved only when the agent uses a user token.
  • Backstage does not consult permission policies for service principals. ContextVerity records the decision basis (permission-policy or service-principal) so the receipt does not overstate what was checked.

Time of check, time of use

A verdict describes state at verification time. A change can land between a VALID verdict and the action it gates. Keep TTLs short and verify as close to the action as you can.

ContextVerity

ContextVerity is an independent Apache-2.0 open-source project built using open technologies from the Backstage, Kubernetes, CNCF and Linux Foundation ecosystems. It is not a CNCF project and not an official Backstage project.

Backstage, OpenTelemetry and Model Context Protocol are projects of their respective foundations and are named here only to describe integrations. This site uses no cookies, analytics or third-party resources.
