Why ContextVerity

Agents act on context they were handed earlier. The platform keeps moving after the handover.

An agent triaging an incident asks the developer platform who owns payments, which API it provides and what it depends on. That answer is cached, passed between tool calls and reused minutes or hours later. Meanwhile ownership moves to another team, an API definition changes, a permission is revoked, or the service is reclassified as restricted.

ContextVerity records the context an agent received, the source state and permissions that shaped it, and later verifies whether that context is still current and allowed before it is reused.

It detects configured source and authorization drift before receipt reuse. The answer is deterministic and explainable: a verdict plus typed drift codes with before and after values. No language model takes part in any decision.

What it is

  • A context resolver and receipt service for Backstage
  • Typed drift detection over catalog, permission and policy state
  • Three verdicts: VALID, REFRESH, DENY
  • An explicit check an agent calls before acting

What it is not

  • Not an AI firewall, gateway or MCP server
  • Not a hallucination or prompt-injection detector
  • Not a guarantee about state after verification
  • Not production proven; no production adopters yet

How it works

Resolve once, keep a receipt, verify before every reuse.

  1. Resolve

    The agent or engineer asks for context about a subject, for a purpose. ContextVerity selects the context policy that grants it and checks catalog.entity.read for the caller.

    POST /api/contextverity/v1/resolve
{
  "subject": "component:default/payments",
  "purpose": "incident-triage",
  "categories": ["ownership", "apis",
                 "dependencies"]
}

  2. Receive context and a receipt

    Normalized catalog records are digested with SHA-256 over canonical JSON. An immutable receipt is stored server-side with an HMAC-SHA256 integrity tag, and returned with the context.

    {
  "receipt": {
    "receiptId": "…",
    "subject": "component:default/payments",
    "validUntil": "…",
    "snapshotDigest": "sha256:…"
  },
  "context": [ … ]
}

  3. Verify before reuse

    Before acting on that context again, the agent verifies the receipt. ContextVerity re-checks binding, intent, policy, TTL and permissions, re-fetches sources, and compares.

    POST /api/contextverity/v1/receipts/:id/verify

{ "verdict": "REFRESH",
  "drift": [{ "code": "OWNER_CHANGED",
              "effect": "REFRESH",
              "before": "group:default/team-payments",
              "after": "group:default/team-commerce" }] }

Backstage

ContextVerity is a set of Backstage 1.55 plugins. It reads from the platform you already run and uses its permission model.

Software Catalog
The context source: owner, lifecycle, dependencies, provided APIs, API definition digest, the TechDocs reference annotation and the contextverity.github.io/classification annotation.
Permission Framework
catalog.entity.read is checked for the caller at resolve and re-evaluated at verify. Receipts are protected by contextverity.receipt.read.
Actions Registry
Registers contextverity:resolve-context and contextverity:verify-receipt.
MCP Actions backend
The official Backstage MCP Actions backend exposes those actions as MCP tools, so agents can call them without a custom MCP server.
Database service
Receipts live in the Backstage database (SQLite for development, PostgreSQL otherwise), with a retention task.
Frontend plugin
A receipts list and receipt detail page with provenance and drift, built for the new frontend system.

  • Bound to a consumer, issuer, subject and purposePresenting it as someone else, to another instance, for another subject or purpose, or for a wider scope yields DENY.
  • Grant recorded with a digestIf the policy is removed or narrowed below the receipt, verification yields DENY. A semantically equivalent rewrite does not invalidate it.
  • Per-source digestsEach normalized source record is digested over canonical JSON, so verification can name exactly which field changed.
  • Permission basisEach decision records how it was reached, including when Backstage did not consult a permission policy because the caller was a service.
  • Server-authoritativeVerification uses the stored receipt, not a copy the client sends back. Tampering with the stored record fails the integrity check.

Drift

Verification produces typed drift codes. Each carries an effect of NONE, REFRESH or DENY, and the verdict is the strongest effect.

VALID
The context still matches source, permission and policy state at verification time. It is not a promise about later.
REFRESH
No longer current, but not prohibited. Re-resolve before acting.
DENY
Current authorization, classification, policy or binding no longer permits this context.

Known limitations

Stated up front, because a verification tool is only useful if you know exactly what it checks.

  • Verification is point-in-timeVALID means the state matched when verified. Changes between verification and action (TOCTOU) are possible; verify close to the action.
  • Integration is explicit and advisoryBackstage has no supported hook to intercept other plugins' actions. Agents must call verify before acting.
  • Service principalsBackstage does not consult permission policies for service principals. The receipt records that basis instead of implying a policy check.
  • Agent identity over MCPThrough the MCP Actions backend, a static-token agent is forwarded as plugin:mcp-actions. Per-agent identity is preserved only for user tokens.
  • TechDocs contentOnly the TechDocs reference annotation is tracked. Documentation content provenance is not implemented.
  • Source truth is trustedIf the catalog itself is wrong or compromised, ContextVerity faithfully records the wrong state.
  • Synthetic evaluation onlyResults come from synthetic scenarios on a single machine. There are no production adopters.
